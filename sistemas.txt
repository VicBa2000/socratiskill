1. SYSTEM OVERVIEW
================================================================

Socratiskill turns Claude Code into an adaptive socratic mentor
WITHOUT modifying the binary. The logic lives in three layers:

  1. Files (markdown rules + JSON data) that the model reads.
  2. Hooks (bash / TypeScript scripts) that inject context and
     persist telemetry per turn.
  3. State on disk (`~/.claude/socratic/`) that the model consults
     as each session starts.

Since v0.5 there is ONE axis and one dial inside it:

  - LEVEL (1-5): how much of the work is the user's. Changes
    slowly, driven by accumulated evidence or manual override. It
    decides what the agent may author, and the gate enforces that
    part rather than merely asking for it.

  - RUNG (0-5): how much help the user gets while doing their half.
    Changes quickly based on successes/failures within the session,
    bounded by the level's allowed range.

Through v0.4 there were three pedagogical axes plus two escape
valves. They were not really independent: in all ten level x mode
combinations the agent wrote the code, and the level only varied how
much it explained. The axis measured pedagogical overhead, never
authorship — so "you type this one" had nowhere to live and had to
be bolted on as a separate mode, which then needed its own valve,
its own window and its own report. Those four switches were all
descendants of one missing capability.

Each turn, the `UserPromptSubmit` hook injects a block named
"SOCRATIC CONTEXT" into the model's context. On turn close, the
`Stop` hook parses the response, extracts telemetry, and updates
state.


================================================================
2. THE AXIS (L1-L5, plus the L6 off ramp)
================================================================

There is ONE pedagogical setting. It answers one question:

        HOW MUCH OF THE WORK IS THE USER'S?

Everything else — how much the agent explains, which rungs it may
use, what it hands over — is a consequence of the answer, not a
second dial.

CONTRACT (data/levels.json; frozen in unificacion.txt section 12.B).
If a rules file contradicts this table, the rules file is wrong.

  NIV  AUTHORSHIP                    FILES/DAY  STMT/FILE  RUNG   HANDOFF
  ---  ----------------------------  ---------  ---------  -----  ----------
  L1   implements completely            inf        inf      5     none
  L2   structure + trivial bodies         8          8      4-5   module
  L3   skeletons and signatures           6          0      3-4   unit
  L4   nothing                            4          0      2-3   subproblem
  L5   nothing                            3          0      0-1   none
  L6   everything, no pedagogy          inf        inf      -     none

  FILES/DAY  new files the agent may CREATE per UTC day
  STMT/FILE  executable statements allowed in each created file
  RUNG       range of ladder rungs; the rung moves inside it
  HANDOFF    the unit of work handed to the user

INVARIANTS no level may violate:
  I1  Editing an EXISTING file: DENIED on L2-L5, no exception.
      (allowed only on L1 and L6)
  I2  The 80-line-per-file cap applies on L2-L5.
  I3  Budget exhausted -> the gate denies and says the remaining
      count. No override except `ship`.
  I4  A DENIAL never consumes budget. Being told no is not a use.
  I5  L6 disarms layers 1 and 2; layers 3 and 4 remain but report
      "not applicable".

WHY THE NUMBER GOES THIS WAY. Promotion takes work away from the
agent and gives it to the user. Through v0.4 it was the opposite:
L5 was a "silent colleague" that wrote your code without asking,
so competence was rewarded with LESS practice. For a plugin whose
purpose is fighting skill atrophy, that direction was training the
disease.

WHY THE RUNG IS NOT FOLDED INTO THE LEVEL. Two different
timescales. The LEVEL is a stable band that moves by calibration
over days; the RUNG is the reaction inside a single problem, which
climbs after two consecutive failures and comes back down over
minutes. Folding them would mean getting stuck on one bug demotes
you — exactly the noise the weighted calibration of Fase 12 was
built to remove. The level bounds the range; the rung moves inside.

ROLE PER LEVEL (see skills/socratic/rules/level-N-*.md):

  L1 Implementer — the rescue level. The agent writes the code, but
     every line has to teach: interleaved explanation, one real
     comprehension question per block ("¿qué pasa si el email viene
     con espacios?", never "¿se entiende?"). Writing silently is L6,
     not L1.

  L2 Framer — the first level where the user's hands are on anything
     that matters. The split is not "easy vs hard", it is
     LOAD-BEARING vs NOT. A five-line function encoding the actual
     domain rule is the user's; a thirty-line config object is the
     agent's.

  L3 Architect — the working level for a competent developer who
     wants to stay one. Zero statement allowance is the definition
     of the level, not a technicality: a file it creates holds
     imports, types, signatures, comments and TODOs. Nothing that
     runs.

  L4 Guide — writes nothing. The small file budget that survives is
     TEDIUM RELIEF ONLY (an empty package.json, a blank component),
     never structure that carries the design. Rung 2 is the
     distinctive move: point at an analogous case ALREADY SOLVED in
     the user's repo. The agent has Read/Grep; a supermarket-queue
     analogy wastes that.

  L5 Socratic — the top. Questions only, orientation at most after
     two failures. Does NOT decompose — that is a level-4 move and
     the most common leak. When the user is genuinely stuck past
     rung 1, the honest move is saying the problem sits above this
     level and letting them drop to L4, not quietly coaching like an
     L4 while calling it L5.

  L6 Autopilot — see section 15.


================================================================
3. THE LADDER (0-5) — THE DIAL INSIDE THE LEVEL
================================================================

Modes (learn / productive) are GONE. `productive` said the same
thing the level now says, and "I need to ship right now" became
`ship`; `learn` was then the only remaining value of the field and
said nothing the level did not.

The ladder is the same state machine it always was:

  - Escalation:        2 consecutive failures -> +1 rung
  - Zero-knowledge:    "no sé" -> jump to the top rung the level allows
  - De-escalation:     a correct answer drops it (5->3, 3+->1, 1+->0)
  - Ceiling:           rung 5 is a WORK ORDER, never code

What changed is what each rung MEANS, because above L1 "more help"
can no longer mean "more code":

  0  Pure socratic   Ask only. Nothing else.
  1  Orientation     Name the area/file. Not what to do there.
  2  Analogy         Point at a case already solved IN THEIR REPO.
  3  Reduction       2-4 ordered subproblems. Do not solve the first.
  4  Explanation     Prose, then make them restate it before typing.
  5  Work order      Files, signatures, acceptance criteria, edge
                     cases, order. STILL NOT CODE.

THE LITMUS TEST, applicable to all six rungs:

    If the user could copy your response into their editor and get
    working code, you failed — no matter which rung you were on.

The single exception is L1, where the agent is supposed to write;
there the ladder governs how much it EXPLAINS while writing.

================================================================
4. LADDER MECHANICS (state machine)
================================================================

Section 3 defines what each rung MEANS. This one is the machine
that moves it.

Implementation in scripts/hint-state.ts; the rung is then clamped
into the level's allowed range by Axis.clampRung (axis-state.ts),
so the level bounds the ladder and the ladder moves inside it.
Behavior description in skills/socratic/rules/ladder.md.

INITIAL RUNG per level (before clamping):

  L1 -> 5     L2 -> 4     L3 -> 2 (clamped up to 3)
  L4 -> 1 (clamped up to 2)       L5 -> 0
  L6 -> no ladder; the axis is off

AUTOMATIC ESCALATION (scripts/hint-state.ts:processResponse):

  - Correct response -> consecutiveSuccesses++, failures = 0.
    Immediate jump-down:
      5 -> 3     (down by 2)
      3-4 -> 1   (down by 2-3)
      1-2 -> 0   (down by 1-2)
    zeroKnowledgeActive clears.

  - Incorrect response -> consecutiveFailures++, successes = 0.
    If consecutiveFailures >= 2 (ESCALATION_THRESHOLD):
      ascend +1 level.
      reset failures to 0.

  - Zero-knowledge detected (see Detectors) -> jump directly to 5.
    Resets both counters. Sets zeroKnowledgeActive=true.

Clamped to [0, 5]. The hint_state is persisted per session in
sessions/<YYYY-MM-DD>.json and reset on level change via /accept
(accept-calibration.ts:95) or /level N.

Manual adjustment available:

  /socratic hint      -> +1 (more direct)
  /socratic faster    -> +1 (alias)
  /socratic slower    -> -2 (more socratic)


================================================================
5. CALIBRATION SYSTEM (LEVEL UP / LEVEL DOWN)
================================================================

Engine: scripts/record-turn.ts (runs in the Stop hook on turn
close) + scripts/accept-calibration.ts (runs on /accept).

Surface: scripts/build-context.ts injects the suggestion to the
model when pending_calibration_change exists.

Guiding principle: the system NEVER changes the level on its own.
It only:
  - Detects the pattern -> enters the diagnostic (UP) or suggests
    (DOWN).
  - Injects the suggestion to the model.
  - The model proposes the change to the user.
  - The user confirms with /accept (or bypasses with /level N).


--- 5.1 PER-TURN TELEMETRY (HINT_META) ---

At the end of EACH response the model emits a hidden block
(HTML comment, invisible to the rendered output) with per-turn
telemetry:

  <!-- HINT_META {
    "topic":"closures",
    "correct":true,
    "domain":"lenguajes",
    "hintLevel":2,
    "readiness":"at"
  } /HINT_META -->

Fields:

  topic       short slug for the main concept discussed (null if
              none).
  correct     true  -> user demonstrated understanding
              false -> user failed / was confused
              null  -> not applicable (general question, coding
                       task with no eval)
  domain      one of the 7 taxonomy keys (see section 7).
  hintLevel   0-5, how direct the model was THIS turn.
  readiness   (optional)
              "above" -> answered above the current level
              "at"    -> answered at level
              "below" -> fell below the level
              null    -> no judgment
  feynman_gap (required while Feynman mode is active, see
               section 9) short phrase describing a detected gap,
               or null.
  diagnostic  (required during diagnostic mode, see 5.4)
              "pass" / "fail" / null.

Parsing: record-turn.ts extracts with a regex (accepts the new
HTML-comment form and the legacy `[HINT_META]...[/HINT_META]`
form). Validation via state-io.ts:isHintMeta (rejects JSON that
parses but has the wrong shape).

Persistence: each turn is appended as a TurnRecord to
sessions/<YYYY-MM-DD>.json with turn_index, timestamp, excerpts
(truncated to 200 chars), and the HINT_META fields.


--- 5.2 PER-LEVEL THRESHOLDS ---

In data/algorithm.json:

  calibration_cooldown_turns: 5
    Minimum turns between consecutive evaluations. Prevents two
    consecutive turns from triggering two pending changes.

  calibration_up_by_level (window / required correct):
    L1 -> window 12, correct_required 10
    L2 -> window  9, correct_required  7
    L3 -> window  7, correct_required  5
    L4 -> window  7, correct_required  5

  calibration_down_by_level (window / required wrong):
    L2 -> window 5, wrong_required 3
    L3 -> window 5, wrong_required 3
    L4 -> window 5, wrong_required 3
    L5 -> window 5, wrong_required 3

Rationale:
  - L1 requires more sustained evidence (10/12) to avoid
    promoting a novice after an easy streak.
  - Higher levels have shorter windows — evidence accumulates
    faster.
  - Downgrade is uniform 3/5 — "stuck above level" is worse
    than a false downgrade (can be corrected by leveling back up).

Only turns with correct=true or correct=false count toward the
window. Turns with correct=null do not.


--- 5.3 QUALITY FILTERS BEFORE TRIGGERING UP ---

Meeting the numeric threshold is NOT enough. Three additional
filters (all in evaluateCalibration()):

FILTER A — Weighted average >= 0.5

  Each correct is weighted by the hint under which it was
  resolved:

    weight = (5 - hintLevel) / 5

  Adjusted by readiness:
    "above" -> +0.25 (capped at 1.0)
    "below" -> -0.25 (floored at 0.0)
    "at" / null -> no adjustment

  Examples:
    correct at hint=0 + readiness="above" -> 1.0
    correct at hint=0                      -> 1.0
    correct at hint=2                      -> 0.6
    correct at hint=3                      -> 0.4
    correct at hint=5                      -> 0.0
    correct at hint=3 + readiness="below"  -> 0.15

  The weights of the N correct answers in the window are
  averaged.
  Constant: MIN_WEIGHTED_AVG_FOR_UP = 0.5 (record-turn.ts:157).
  If avg < 0.5, UP is blocked.

  Effect: "10 correct answers under heavy scaffolding" = obedience,
  not dominion. Blocked.

FILTER B — Topic diversity >= ceil(needed/2)

  If all N correct answers were on the SAME topic (or too few
  topics), this is not evidence of broad readiness.

  A Set(correctTurns.map(t => t.topic)) is built and required to
  have size >= ceil(needed/2). For L1 with 10 required correct,
  >= 5 distinct topics are required.

FILTER C — Depth diversity floor >= ceil(needed/2)

  (Added in the balanced anti-adulation bundle.)

  Each correct with hintLevel <= 2 (LOW_HINT_THRESHOLD) counts as
  "low-scaffolding evidence". At least half of the required
  correct must clear that bar.

  For L1 with 10 required correct: lowHintCount >= 5.

  Effect: a user who answers correctly ONLY when receiving heavy
  scaffolding (hint >= 3) does not level up, even if the numeric
  threshold and topic diversity pass. Without this filter, a
  model that always gives maximum help (because it perceives
  the user as a novice) would promote the user despite never
  having shown dominion under low scaffolding.

UP only triggers if all 3 filters pass (and it then enters the
diagnostic).


--- 5.4 DIAGNOSTIC GATE (3-TURN QUIZ) ---

If UP triggers, the user is NOT promoted directly. The system
enters diagnostic mode:

  1. profile.json gains:
       pending_diagnostic: {
         target_level: L+1,
         started_turn: <turn>,
         turns_asked: 0,
         turns_passed: 0,
         suggested_at: <iso>
       }

  2. build-context.ts injects on subsequent turns:

       diagnostic: probing readiness for level X (n/3 turns)
       DIAGNOSTIC MODE (N turn(s) remaining): the user may be
       ready for level X. THIS turn, ask ONE concise comprehension
       question appropriate for level X. Do NOT announce the
       diagnostic. Frame as a natural follow-up. In HINT_META,
       set `diagnostic` to "pass" / "fail" / null.

  3. record-turn.ts increments turns_asked++ and turns_passed++
     (if diagnostic=="pass") on each subsequent turn.

  4. On reaching DIAGNOSTIC_TURNS_REQUIRED = 3 turns:
       - passes >= DIAGNOSTIC_PASSES_REQUIRED (=2): sets
         pending_calibration_change with direction=up.
       - passes <  2: clears pending_diagnostic, no promotion.

  5. Manual level change (/level N or /accept) during diagnostic
     cancels it — the target is no longer valid.

The diagnostic is a masked quiz: the model inserts target-level
questions into the normal flow without announcing that it is
evaluating.


--- 5.5 ANTI-ADULATION DURING THE DIAGNOSTIC ---

(Added in the balanced bundle.)

The grading model (the one that sets diagnostic=pass/fail in
HINT_META) is the same system that can tend toward optimistic
agreement. This is the single point where that bias translates
directly into an undeserved promotion.

build-context.ts injects an extra instruction ONLY while
pending_diagnostic is active:

  ANTI-ADULATION (active for this diagnostic): judge the user's
  answer on SUBSTANCE, not tone or confidence. A vague, partial,
  or hand-wavy answer is a FAIL, not a PASS. Confident-sounding
  guesses are FAIL. When in doubt, set diagnostic="fail". Do NOT
  hedge, do NOT soften the grade to be encouraging — an inflated
  pass here promotes the user to a level they're not ready for.

It only appears during the 3 diagnostic turns — not as a
persistent pressure.


--- 5.6 DOWNGRADE (DIRECT, NO DIAGNOSTIC) ---

If DOWN triggers (3 wrong in the last 5 turns for L2-L5),
pending_calibration_change is set directly, WITHOUT going through
the diagnostic.

Rationale: being stuck above your level is worse than a false
downgrade. If the downgrade is incorrect, the user can easily
level back up with /level N.

The downgrade also does NOT go through the 3 quality filters —
meeting the numeric threshold is enough.


--- 5.7 MANUAL ACCEPTANCE AND BYPASS ---

When pending_calibration_change exists, build-context.ts injects:

  calibration: suggest level X -> Y (reason)
  note: tell the user you notice a pattern and propose running
  "/socratiskill:socratic accept" (or "level Y"). Wait for
  confirmation — do NOT change level yourself.

The model proposes the change to the user. The user decides:

  /socratiskill:socratic accept
    -> accept-calibration.ts:
       1. Lock on profile.json
       2. global_level = pending.to
       3. hint_state reset to createInitialState(newLevel)
          (consecutive counters to 0, currentLevel = the new
          level's initial hint)
       4. Delete pending_calibration_change
       5. Also delete pending_diagnostic (in case it was stale)
       6. Print "calibration accepted: level X -> Y (Role)"

  /socratiskill:socratic level N
    -> Full bypass. Sets global_level=N, ignores the entire
       calibration pipeline. Useful when the user knows which
       flavor they want.

6. PER-TURN DETECTORS
================================================================

scripts/detector.ts runs on every turn (from build-context.ts)
against the user prompt. Its results are injected into SOCRATIC
CONTEXT as `signals: ...`.

Four detectors:

--- ZERO-KNOWLEDGE ---
  26 bilingual regex patterns (Spanish + English).
  Examples: "no se", "ni idea", "no entiendo", "nunca he usado",
  "estoy perdido", "desde cero", "soy nuevo", "primera vez",
  "i don't know", "i'm lost", "from scratch", "first time".

  Effect:
    - If count > 0: signal "zero-knowledge=N" is injected.
    - If count > 0 AND record-turn detects "zk" before eval:
      hint_state jumps to 5 immediately, sets zeroKnowledgeActive.
    - Note to the model: "drop one hint rung and explain the term
      before proceeding".

--- SLOW-DOWN ---
  17 bilingual regex patterns.
  Examples: "mas despacio", "paso a paso", "repite", "me perdi",
  "slow down", "step by step", "can you repeat", "i'm confused".

  Effect:
    - Signal "slow-down" in the context.
    - Note: "pause, summarize, wait for acknowledgment".

--- COPY-PASTE ---
  Weighted heuristic that flags when the user looks like they
  pasted code without understanding it. Factors:

    - >15 lines of fenced code at level <=2: +0.4
    - 3+ fenced code blocks in one message: +0.2
    - Message.length > 5 * prev_message.length: +0.2
    - Sophisticated patterns (await Promise.all, generics,
      try/catch/finally) at level <=2, >=2 patterns: +0.3

  Trigger: score >= 0.4 -> isCopy=true with confidence=score.

  Effect:
    - Signal "copy-paste(conf=X.YY)".
    - Note: "likely copy-paste — ask the user to explain the
      snippet before building on it".

--- TECHNICAL TERMS COUNT ---
  Counts occurrences from a static list
  (data/technical-terms.json). If >= 2: signal "tech-terms=N" is
  injected.

  No attached note — pure telemetry for the model. Useful to
  infer whether the user is using vocabulary above their
  declared level.

7. DOMAIN TAXONOMY
================================================================

scripts/taxonomy.ts + data/domains.json.

7 predefined domains (keys in Spanish for parity with the
original fork; labels in English):

  fundamentos       — Fundamentals (variables, loops, data
                      structures, algorithms, complexity,
                      closures, hoisting)
  lenguajes         — Languages (javascript, typescript, python,
                      go, rust, sql, generics, enums)
  paradigmas        — Paradigms (oop, solid, functional, async,
                      concurrency, observer, monad)
  web               — Web (react, vue, hooks, components, rest,
                      graphql, http clients, css frameworks)
  backend           — Backend (databases, orms, auth, jwt,
                      microservices, message queues, ci/cd,
                      docker, kubernetes)
  infraestructura   — Infrastructure (git, linux, networking,
                      dns, cloud, terraform, security/owasp,
                      tls, monitoring)
  avanzado          — Advanced (system design, design patterns,
                      architecture, performance, caching,
                      scalability, cap theorem)

Matching:
  - Case-insensitive substring match on the user prompt.
  - Keywords <= 3 chars use word-boundary regex to avoid false
    positives (e.g. "db" does not match inside "debug").
  - Score = count of keyword matches.
  - Ranked; top one becomes the `primary domain`.

Effect:
  - `domain: <key> (<label>)` is injected into SOCRATIC CONTEXT.
  - The domain is persisted on each TurnRecord and on ErrorMap
    entries (to group spaced-repetition cards by area).

8. ANTIPATTERNS
================================================================

scripts/antipatterns.ts + data/antipatterns.json.

Automatic detection of antipatterns in fenced code blocks that
appear in user prompts AND agent responses.

Flow (Antipatterns.recordTurn on each Stop hook):
  1. Extract fenced code blocks from user + agent text.
  2. For each defined pattern, count matches (with anti-ReDoS
     timeout).
  3. Update antipatterns.json:
     - occurrence_count += matches
     - consecutive_clean = 0 if there was a match, +1 if not
     - last_seen = now (if there was a match)

Thresholds (configurable via antipatterns.json):
  ACTIVATION_THRESHOLD = 3
  DEACTIVATION_CLEAN_STREAK = 5

Per-antipattern states:
  - inactive by default.
  - On reaching 3 total occurrences: active=true.
  - If active and 5 consecutive turns pass with no matches:
    active=false (but occurrence_count is preserved).

Effect in SOCRATIC CONTEXT (build-context.ts):
  - If there are active antipatterns, it injects:
    "active antipatterns: <id1>(n1), <id2>(n2), ..."
  - Note to the model: "before emitting code, check if the
    snippet would introduce any of these. If yes, rewrite first
    and explain why. If the user's code contains one, call it
    out."
  - `rules:` line includes "antipatterns.md" as an extra.

9. FEYNMAN MODE (ROLE INVERSION)
================================================================

scripts/start-teach.ts, scripts/end-teach.ts.

Invocation: /socratiskill:socratic teach <topic>.

Role inversion: the USER is the teacher; the model is the
student who probes comprehension with concrete questions, edge
cases, and "why not X?".

State (in sessions/<today>.json):
  feynman: {
    topic: "<string>",
    started_at: <iso>,
    gaps: ["gap1", "gap2", ...]
  }

Per-turn effect while feynman is active:
  - SOCRATIC CONTEXT shows: "feynman: teaching X since <time>
    (N gaps logged)".
  - Rules line includes "feynman.md".
  - Note to the model: "FEYNMAN MODE — the USER is the teacher.
    Do NOT explain, do NOT fill gaps. Probe with concrete
    examples, edge cases, and 'why not X'."
  - HINT_META.feynman_gap is REQUIRED: a short phrase describing
    a gap detected this turn, or null if the explanation was
    solid.

Close: /socratiskill:socratic endteach.
  - Compute duration, count gaps, persist feynman_summaries[].
  - The journal (build-journal.ts) harvests the summaries.


----------------------------------------------------------------
9.1 TEMPLATE MODE (DELIVERY, NOT PEDAGOGY)
----------------------------------------------------------------

scripts/template.ts. Invocation:
/socratiskill:socratic template [on|off].

What it is: a way to declare ONCE — instead of renegotiating
every turn — that the agent hands over structure only (real
signature, numbered work order in comments, six parts) and the
USER types the bodies.

State (in sessions/<today>.json, like feynman and drill):
  template: { started_at: <iso>, turns: <n> }
It does NOT touch profile.json and does NOT move global_level.
It is a session episode, not a calibration change.

IT DOES NOT LOOSEN THE GATE, in either direction:
  - It never denies anything the level allowed. The mode is
    opt-in; whoever turned it on already decided. Enforcement was
    built (v0.5.3-dev) and reverted on purpose — level 1 is the
    RESCUE level and is the worst possible place for a wall.
  - It never permits anything the level denied. Injecting it at
    L5 would turn "asks only" into "hands over skeletons", which
    is the one thing no delivery mode may do.

Per-level effect (build-context gates the wording by level):
  L1   OVERRIDE of the level's delivery. L1 normally writes the
       code; with the mode on it hands over structure and the
       user writes the bodies. This is the case the mode exists
       for.
  L2-L3 FORM ONLY. These levels already deliver skeletons; the
       mode fixes their shape. It does not authorize one extra
       line.
  L4-L6 Not injected at all. L4 delivers no skeleton, and L6 is
       the axis switched off. `template on` above L3 says so
       instead of leaving a switch the user thinks is on.

Also fixed by this mode: at L1, HINT_META.user_wrote used to be
requested only when the gate was armed — which L1 never arms. So
the turns where the user wrote ALL of the code were exactly the
ones recorded as user_wrote:null. L1 now records authorship.

KNOWN RESIDUE (level contract, not a bug in the mode): at L3 the
template in CALL-EXPRESSION form is denied, because
statements_per_file = 0 IS the definition of level 3. The
DECLARATIVE form passes — the numbered work order moves above the
signature and there is no body to fill. Both forms are documented
in rules/template.md, and tests/fixtures/template-examples.ts
runs each documented block through the real gate at the level its
marker declares.

Naming note: `scaffold` is RETIRED vocabulary (the v0.4 scaffold
window). S37 bans /\bscaffold\b/ in skills/ and hooks/ so the
dead name cannot come back with a new meaning.

10. LEITNER / SPACED REPETITION (ERROR-MAP)
================================================================

File: ~/.claude/socratic/error-map.json.

Every time HINT_META carries a topic with correct=true/false,
record-turn.ts updates the corresponding entry:

  key = "<topic>::<domain>"
  entry: {
    topic, domain,
    fail_count, success_count, consecutive_correct,
    last_hint_level, resolved, leitner_box,
    last_seen, next_review_at
  }

Transitions:

  correct=false:
    fail_count++
    consecutive_correct = 0
    resolved = false
    leitner_box = 0 (reset)
    next_review_at = now + LEITNER_DAYS[0] (= +1 day)

  correct=true:
    success_count++
    consecutive_correct++
    If consecutive_correct >= 2:
      leitner_box = min(LEITNER_DAYS.length - 1, box + 1)
      next_review_at = now + LEITNER_DAYS[box] days
      If box == LEITNER_DAYS.length - 1: resolved = true

Leitner intervals (data/algorithm.json:leitner_days):
  [1, 3, 7, 14, 30] days
  (box 0 -> 1d; box 1 -> 3d; box 2 -> 7d; box 3 -> 14d;
   box 4 -> 30d + resolved=true)

Effect on SOCRATIC CONTEXT:
  - dueCards() filters entries with next_review_at <= now.
  - If there are >0 due cards, it injects:
    "review due: N card(s) — topic1(fails=n1), topic2(fails=n2), ..."
  - Note: "if the user is idle or asks what to do, suggest
    running /socratic review to practice one overdue card."

Manual review run:
  /socratiskill:socratic review
  -> scripts/pick-review.ts picks the most overdue card and
     returns it; the model asks ONE verifiable question; the
     next turn processes HINT_META with that topic.

12. INJECTION CHANNELS (HOOKS)
================================================================

Hooks are declared in hooks/hooks.json. The install.sh script
adds them to ~/.claude/settings.json as a marker-delimited block
(legacy path only — plugin install registers them automatically).

--- UserPromptSubmit (before the turn) ---

  Script: scripts/hook-pre-prompt.sh -> bun run build-context.ts.

  Input: JSON via stdin with {session_id, prompt, cwd, hook_event_name}.

  stdout output: the SOCRATIC CONTEXT block, which Claude Code
  injects into the model context with the prefix:
    "UserPromptSubmit hook success: <content>"

  Block content:
    level: N (Role) — <summary>
    authorship: <what you may create / edit, budget left today>
    rules: follow skills/socratic/rules/level-N-*.md + axis.md
           + ladder.md [+ extras: feynman.md, template.md, ...]
    [feynman: ... ]
    [template: ON since <iso> (N turn(s)) — the user writes the
     bodies]
    domain: <key> (<label>) | (none detected)
    [hint: N (name) [zk-active]]
    signals: <zk / slow-down / copy-paste / tech-terms / (none)>
    [active antipatterns: ... ]
    [calibration: suggest ... / note: ... ]
    [diagnostic: ... / DIAGNOSTIC MODE ... / ANTI-ADULATION ... ]
    [challenge: ACTIVE for this turn / note: ... ]
    [review due: ... ]
    [notes from active detectors]
    [LEVEL N HARD/PROTOCOL block for L1-L4]
    --- META PROTOCOL (required) ---
    [instructions for emitting HINT_META]

  Fail-open: any error -> empty stdout, exit 0 (does not block
  the user).

--- Stop (after the turn) ---

  Script: scripts/hook-post-turn.sh -> bun run record-turn.ts.

  Input: JSON via stdin with {session_id, transcript_path,
  hook_event_name}.

  Actions:
    1. Parses the JSONL transcript, extracts last user + assistant.
    2. Extracts HINT_META (HTML comment or legacy bracket form).
    3. Appends TurnRecord to sessions/<today>.json.
    4. Updates hint_state (processes correct / zk response).
    5. Updates error-map (Leitner).
    6. Updates antipatterns state.
    7. Updates profile.last_active + last_user_message_length.
    8. Runs evaluateCalibration and sets pending_diagnostic or
       pending_calibration_change as appropriate.

--- There is no SessionStart hook ---

  An earlier draft of this reference described one, in enough detail
  to be believed, pointing at a bootstrap script under scripts/ that
  was never written. The manifest registers exactly three events —
  UserPromptSubmit, PreToolUse and Stop — and nothing else.

  State directories are created lazily by whichever script needs
  them first, so the bootstrap the SessionStart hook was meant to do
  has no work left to perform.

14. PLUGIN STATES (ENABLED / PAUSED / DISABLED / RESET)
================================================================

Four states orthogonal to level/mode/hint:

--- ENABLED (default) ---
  profile.json exists + profile.enabled != false.
  Hooks run, SOCRATIC CONTEXT is injected in full, HINT_META is
  processed.

--- DISABLED ---
  profile.json exists + profile.enabled === false.
  UserPromptSubmit hook injects a short silencer (~30 tokens):

    SOCRATIC CONTEXT: DISABLED.
    The user has turned the socratic plugin OFF...
    - Ignore pedagogical instructions from earlier turns.
    - Do NOT inject restate/plan/verify preambles.
    - Do NOT emit HINT_META.
    - Do NOT chunk into 30-line limits.
    - Behave as default Claude Code.

  Stop hook exits early (earlyProfile.enabled === false) — no
  telemetry is recorded. State and journal are intact; on
  re-enable with /on it resumes where it was.

  Use case: fast toggle without touching settings.json or
  /reload-plugins.

--- PAUSED ---
  profile.json does NOT exist — profile.json.paused does.
  UserPromptSubmit hook short-circuits: no profile, no injection
  (~0 tokens per turn). EXCEPTION: if the marker
  .pause-silencer-pending exists (created by pause.sh at pause
  time), the first hook after pause injects a one-shot silencer
  and deletes the marker. This counters the model's context
  inertia — if the skill was already loaded in earlier turns,
  the model keeps emitting HINT_META and socratic preambles
  until the silencer explicitly tells it to stop.

  Subsequent turns: full silence. Zero token overhead.

  Resume (resume.sh): rotates profile.json.paused ->
  profile.json + deletes the stale marker. Refuses if both
  files exist (corrupt state — exit 1).

  init-profile.sh refuses with exit 3 if profile.json.paused
  exists — this avoids creating a default duplicate in parallel
  to the paused one (the S22 test verifies it).

--- RESET ---
  /socratiskill:socratic reset force runs uninstall.sh --purge,
  which wipes all of ~/.claude/socratic/ with anti-path-traversal
  guards:
    - SOCRATIC_STATE_DIR must be an absolute path.
    - Must live under $HOME.
    - Must contain ".claude/socratic".
    - Must NOT contain ".." segments.
    - Cannot be $HOME itself, /, /root, /home, /Users, /tmp.

  The plugin remains installed (settings.json keeps the hooks),
  but with no profile.json the hook injects nothing. A fresh
  calibration (/calibrate) starts clean.

  To uninstall completely:
    /plugin uninstall socratiskill
    /plugin marketplace remove socratiskill

14.1 A FIFTH STATE: INCONSISTENT (and `repair`)
----------------------------------------------------------------

scripts/profile-health.ts (detection), scripts/repair.ts (command).

The four states above are the ones a USER chooses. This one a BUG
produces, and it is the only one that looks exactly like a
healthy state from inside a session.

HOW IT HAPPENS. Until v0.5.3 the Stop hook wrote profile.json
even while paused, rebuilding it from an empty object. That
file has no global_level, so Axis.readLevel returns the default
of 3 — and build-context then MIGRATES it, writing
global_level: 3 for real. So the wrong level is persisted, not
merely defaulted: it survives a restart and is indistinguishable
from a calibration the user never performed. Meanwhile the real
profile sits in profile.json.paused, and resume refuses to act
with two profiles present.

UPDATING THE PLUGIN DOES NOT FIX THIS. The code fix stops new
damage; the residue on disk stays until something removes it.
That distinction is the whole reason this section exists.

THE ARTIFACT FINGERPRINT — all three required, because this
enables a DELETION and a false positive costs a real calibration:
  1. `last_user_message_length` present — written ONLY by
     record-turn, so it is the positive signature of the Stop
     hook having authored the file.
  2. `calibration_completed !== true` — excludes anyone who ran
     calibrate. Without this the test eats real profiles, since
     a calibrated profile accumulates the key above too.
  3. No init-profile key (mode, comprehension_speed,
     copy_tendency, streak_days) — covers the user who never
     calibrated but whose profile was still created properly.

DIAGNOSES:
  ok           nothing to do.
  resurrected  both files, active one is an artifact. The only
               case with an obvious right answer, so the only
               one `--apply` resolves.
  ambiguous    both files, active one holds real settings.
               Refuses even with --apply (exit 3) and prints
               both: choosing for the user here is the exact
               mistake the command exists to prevent.
  orphan       only the artifact; the .paused is already gone.
               Nothing to restore, but the level on screen is
               fictitious and must be said out loud.

WHERE IT IS DETECTED. Not at install: install.sh is the legacy
path and a plugin install never runs it. The only entry point
that executes on every install route and every turn is
build-context, so the warning is injected there — every turn
while it lasts, immediately after the level line, because it is
the one line in the block that revokes the authority of the
others.

THE RUNNING VERSION. `repair` always prints the version read
from the manifest sitting next to the scripts being executed,
even when there is nothing to repair. That is NOT what /plugin
reports: /plugin says what the marketplace resolved, this says
what is running, and the two diverge when an update did not
refresh the installed copy. It is the first hypothesis to rule
out whenever a shipped fix appears not to work.

  Empirically (September 2026): Claude Code caches plugins under
  ~/.claude/plugins/cache/<mkt>/<plugin>/<VERSION>/, one
  directory per version. So the path this line prints already
  contains the running version twice over, and a stale install
  shows up as a path ending in the old number.

WHEN THE DAMAGE HAPPENED. The diagnosis also prints the
artifact's `last_active`: the moment the Stop hook wrote it.
Two opposite conclusions look identical without it —

  timestamp BEFORE the update: leftover state. The code fix
    works and the residue merely outlived it. This is what
    `repair` is for.
  timestamp AFTER the update: a live path the fix did not
    close, and a real bug report.

It is printed BEFORE any mutation on purpose, because `--apply`
deletes the artifact and takes that evidence with it. A repair
tool that destroys the only record of what it repaired makes the
next occurrence undiagnosable.

15. THE AUTHORSHIP GATE (v0.5)
================================================================

The only HARD enforcement in the plugin. Everything else is text
injected into the context and obeyed at the model's discretion; this
one is a PreToolUse hook that refuses the call outright.

Why it cannot rest on obedience: a level-1 turn once wrote 378 lines
despite explicit limits (cambios.txt, Tarea 10.A.2). "You do not
write this" is not a rule a helpfulness gradient respects.

15.1 THE MECHANISM
------------------
Claude Code lets a PreToolUse hook deny by printing
{"hookSpecificOutput":{"hookEventName":"PreToolUse",
  "permissionDecision":"deny","permissionDecisionReason":"<txt>"}}
The tool never runs (verified: the canary file was never created —
this is a denial, not a rollback) and the model receives <txt> clean.

Entry point: scripts/hook-pre-tool.sh -> scripts/gate-tool.ts

15.2 THE THREE LAYERS
---------------------
LAYER 1 — CREATE vs EDIT. The only authorship boundary drawable
without anyone's opinion. "Is this boilerplate or the code that
teaches them?" is a judgment, and a judgment handed to the model is
one its helpfulness gradient widens until the exception swallows the
feature. Whether a file already exists is a fact.

LAYER 2 — SHAPE (scripts/shape-check.ts). Closes the hole layer 1
leaves: nothing stops the agent from creating a file that does not
exist and putting the whole implementation inside it.

  THE FRAMING THAT WORKS. Do not try to DETECT an implementation —
  that is open-ended and semantic, and a model can out-invent any
  blacklist. Assert the closed property instead: "this HAS THE SHAPE
  OF A SKELETON".

  Every line is classified into exactly one of blank / comment /
  structural / import / declaration / marker / STATEMENT, and
  STATEMENT is the RESIDUAL category. Unknown syntax, an unlisted
  language, a construct nobody anticipated: all of it lands in
  STATEMENT and consumes allowance. The check FAILS CLOSED by
  construction, not by enumeration.

  A statement line is worth one segment per top-level `;` (quote
  aware), because counting one-per-line let a whole implementation
  be packed onto a handful of lines under the 80-line cap.

  Markup (.html/.json/.css/...) is judged by the line cap alone: it
  has no bodies to leave empty, so a statement budget would deny
  every honest scaffold. Everything unrecognized is treated as CODE,
  which is the strict side.

  VOCABULARY (v0.5.2). Failing closed is safe, but it is only USABLE
  if the recognizer speaks the language in front of it. Measuring
  that showed the original regexes spoke FOUR languages — TS/JS,
  Python, C#, Java — while code_extensions listed twenty. Nine of
  thirteen honest skeletons were denied, and since the allowance is 0
  at levels 3-5 a single false positive kills the whole file: eleven
  extensions were effectively unusable. There were zero false
  negatives, so the design was right and only the vocabulary was
  missing.

  The fix added vocabulary, NOT a softer polarity, under two rules:

    - LANGUAGE-SPECIFIC RULES ARE GATED BY EXTENSION. A rule that has
      to be loose to be useful (SQL column definitions, Go's
      colon-less struct fields) runs only for its own language, so it
      cannot loosen TypeScript. "generic" is the strict fallback and
      is what any unrecognized extension gets. The language comes
      from the PATH, never the content — otherwise the agent could
      pick its own ruleset by writing a shebang.
    - EVERY LOOSE RULE IS GUARDED BY A STATEMENT-KEYWORD DENYLIST.
      `Email string` and `return nil` have the same two-token shape;
      the keyword that introduces execution is the only thing that
      separates them, and the denylist is checked first.

  For .sql specifically: DDL (CREATE/ALTER/DROP of a schema object),
  column definitions, procedure parameters and session pragmas are
  structure. SELECT/INSERT/UPDATE/DELETE/MERGE/EXEC stay statements,
  so the BODY of a stored procedure is still the user's to write —
  which is the point.

  Scenario S36 measures both directions and will not pass a checker
  that simply denies everything; tests/fixtures/shape-why.ts pins 60
  line-level contracts so a widened regex cannot quietly swallow a
  statement.

LAYER 3 — DAILY BUDGET. Does not prevent, it bounds the blast
radius: N new files per UTC day by level, 80 lines each. Replaces
v0.4's user-granted scaffold window — the gate never needed the
model's opinion, only a fact and a counter.

LAYER 4 — LEDGER + VISIBILITY. Every file the gate allows is counted
and SUBTRACTED from the autonomy report. Strong property: even if
layers 1-3 are fooled, the METRIC stays honest, because those lines
are attributed to the agent anyway. `status` shows the daily count,
so the user is the last check — with a number, not with faith.

15.3 POLARITY WARNING (do not "harmonize")
------------------------------------------
Two detectors, opposite tunings, for a principled reason:

  detectDisguisedWrite (gate-tool.ts)  PERMISSIVE — when in doubt,
    ALLOW. A false positive blocks the USER from running their own
    tests, which is the activity the whole axis exists to produce.

  shape-check.ts                       RESTRICTIVE — when in doubt,
    DENY. A false positive only blocks the AGENT, which retries with
    a thinner file and loses a turn.

The cost of an error is asymmetric in opposite directions. Both
files carry this note at the point where someone would "fix" it.

15.4 WHAT IS BLOCKED
--------------------
  Write to an existing file      denied (that is an edit)
  Write to a new file            allowed if shape + budget + cap pass
  Edit / MultiEdit / NotebookEdit denied (they only touch existing)
  Agent / Task                   denied (a subagent writing is the
                                 agent writing)
  Bash                           inspected: `>` redirects, tee,
                                 sed/perl/ruby -i, awk -i inplace,
                                 dd of=, truncate, patch, git apply,
                                 writeFileSync/createWriteStream/
                                 open(...,'w') in inline node|python.
                                 /dev/null, /dev/stderr and fd
                                 redirections (2>&1, >&2) excluded —
                                 that is plumbing, not authoring.

15.5 FAIL-OPEN PATHS
--------------------
A gate that blocks real work by mistake gets the plugin uninstalled,
so every uncertain path allows the call:

  - no profile, unreadable profile, enabled=false
  - level 1 (the agent is supposed to write)
  - level 6 (the axis is off)
  - an open `ship` escape
  - any exception anywhere in the engine

THE LOCKED-ROOM EXEMPTION. Writes inside the state dir are always
allowed, because `socratic off`, `level N` and `challenge` mutate
profile.json through the Write tool — gating that path would let the
axis block the very commands that change it. The comparison uses
resolve() (so a ".." path cannot walk out) and a separator boundary
(so ".../socratic-backup" is NOT exempted by prefix).

15.6 COST
---------
The hook fires on EVERY Write/Edit/Bash of every session because it
is registered in the manifest. The disarmed path is written in bash
builtins only — no cat, no grep, no forks — and parses global_level
with parameter expansion, arming only on 2-5.

  bare `bash -c 'exit 0'`   ~64ms   <- the floor, not ours
  short-circuit (disarmed)  ~98ms
  full gate (armed)        ~490ms   (dominated by the bun spawn)

15.7 LEVEL 6 — THE OFF RAMP
---------------------------
Not the continuation of the axis: its APAGADO. From L1 to L5 the
number is monotonic ("how much of the work is yours"); 6 jumps back
past L1. Anything assuming monotonicity must branch on it rather
than read it as "even more than 5".

  R6.1  Calibration CLAMPS AT 5 and can never promote here, by any
        path (continuous, diagnostic gate, or `accept`). A plugin
        fighting atrophy that promotes you to "I do everything"
        sabotages itself. The only way in is typing `level 6`.
  R6.2  Calibration does not run while here. There is no evidence to
        gather about someone not being asked for anything.
  R6.3  The gate is fully disarmed.
  R6.4  The autonomy report says "not applicable", never "+0 lines".
        A zero that means "not measured" is the dishonest datum the
        report exists not to produce.
  R6.5  `status` ALWAYS reports it by name, with what it implies and
        where the real axis lives. Discouraging discovery is not the
        same as hiding state from someone who already turned it on.
  R6.6  No commentary on being here — same rule as the escape.

Discretion, concretely: absent from argument-hint, README's
subcommand table and QUICKSTART; present in this file, in
data/levels.json, and in README's per-level protocol table. The
validator accepts 6 without offering it; 7+ errors listing "1-5".

RISK BEING WATCHED (RU-2): level 6 and `ship` overlap in intent.
`ship` is temporary, demands a reason and is logged; level 6 is
persistent, silent and leaves no trace in the metric. It could
become a permanent escape that hollows the plugin out. The only
available signal is time spent there, reported plainly in the
journal under "days at level 6".

15.8 THE ESCAPE (`ship`)
------------------------
scripts/escape.ts. Deduplication of v0.4's `unlock` (temporary,
reason required, logged) and `mode: productive` (persistent,
silent) — both were asking "I need to ship right now" and only
differed because they had been invented for different axes.

Reason REQUIRED (it is the whole accountability mechanism), expiry,
log, self re-arming. Refused at L1 and L6 with an explicit message:
there is nothing to escape from when the agent already writes.

NEVER EDITORIALIZED. No "are you sure", no reminder about goals, no
disappointment. Real work has real deadlines, and a lock with no
exit gets uninstalled the first Friday it gets in the way. Flattery
and scolding are the same error of not respecting the decision.

15.9 THE HANDOFF (L2-L4)
------------------------
skills/socratic/rules/handoff.md.

  frame -> name the unit -> acceptance criteria -> STOP
        -> evaluate -> close -> next

Criteria are stated BEFORE any code exists; that is what makes the
review objective instead of a matter of taste. State carried in the
session file (NOT the profile: an abandoned unit must not follow the
user into tomorrow, same reasoning as FeynmanState), opened and
closed via HINT_META.handoff, re-announced by the hook every turn.

A second `open` does NOT displace the first: one unit at a time, and
the first is what the user is still working on. A malformed handoff
degrades to "nothing changed hands" and never costs the turn record.

EVALUATION, the half that decays silently into "looks good":
  order      criteria (by name) -> correctness -> safety -> the rest
             is a footnote
  how        point at the LINE, name the problem, ask what they would
             do. Never produce the corrected version — that is Write
             with extra steps, and the gate does not stop prose.
  praise     specific or nothing. "Buen trabajo" teaches that your
             approval carries no information.
  failures   SOFTENING (a real problem stated as a suggestion is one
             that will not be fixed) and REWRITING IN PROSE (enough
             detail to transcribe is the same failure as pasting).
  a failed unit is HANDED BACK, not fixed. It is the most valuable
  turn in the loop: the only moment the user finds their own gap
  while it is still warm.

15.10 AUTONOMY MEASUREMENT
--------------------------
scripts/autonomy-report.ts. Git is the honest signal, not model
self-report: with the gate armed, what appears in the working tree
came from the user's hands.

FORMULA, and why not the obvious one: committing mid-session moves
HEAD and resets the working-tree diff, so "diff now minus diff then"
goes NEGATIVE exactly when the user was most productive.

    lines = diff(baseline_head..HEAD)   (committed)
          + diff(HEAD)                  (pending now)
          + untracked lines             (git diff HEAD cannot see them)
          - baseline.worktree           (what was already dirty)

BASELINES ARE PER REPOSITORY, ROLLING DAILY. This fixes the v0.4 bug
where the baseline was pinned to whatever directory immersive mode
happened to be switched on in: the user moved to another project and
the report measured the tree they had left. The axis has no
activation to hang a baseline on — it is a persistent level — so the
UserPromptSubmit hook, which receives `cwd` every turn, refreshes the
baseline for wherever the user actually is.

TWO HONESTY RULES:
  - Lines the agent wrote by CREATING a file are subtracted exactly
    (the gate saw every one).
  - Lines it wrote during a `ship` window cannot be told apart from
    the user's in the same tree, so the report SAYS SO rather than
    implying a clean number.

No gamification: no badges, no goals, no streaks, and an explicit
instruction not to editorialize or soften a low count. The honest
number is the product — same reason the calibration grader defaults
to fail.

15.11 HONEST LIMITS
-------------------
  - The gate blocks tool calls, not TEXT. Nothing stops the model
    pasting code into the chat; only the rules forbid it.
  - Nothing stops the user opening a second Claude Code window
    without the plugin. Voluntary training; not policed.
  - The shape check is line-based and no substitute for reading the
    diff. It makes smuggling expensive, not impossible.
  - The axis says nothing about code QUALITY. Writing bad code
    unassisted still trains the muscle.
  - The line count is repo-wide, not feature-scoped.

v0.5.1 — DRILL FIX (September 2026)

New: the third drill. `analyze` trains READING and `build` trains
AUTHORING FROM ZERO; neither trains LOCATING — being handed
unfamiliar code plus a change request and working out where the
change belongs. That is the shape of most real requests and the
first skill to go when an agent does all the navigating.

Two phases, and the first one IS the exercise:
  LOCATE     the agent states one concrete change request and then
             asks WHERE it goes, without naming the function or
             quoting the line. A wrong answer gets a narrowing
             question, never a correction.
  IMPLEMENT  only after `drill.ts --advance`. An ordinary handoff
             from there.

The phase is real state, not prose, and the hook injects a different
note per phase — a phase the model can silently skip is a phase that
will be silently skipped.

HARD SAFETY RULE: a fix drill NEVER plants a defect in the user's
repo. No editing their files, no reverting a commit to hide a bug,
no staging. It works on the code as it is and finds a genuine gap by
reading. If the file offers nothing worth changing, it says so and
cancels — a manufactured exercise is worse than none.

`drill done` reports `located first try: yes|no` flat. That is the
number that says whether the navigation muscle is still there, and
it is not a failure to soften.

Changed: drill.ts (kind "fix", phase, --advance/--miss),
build-context.ts (per-phase note), rules/drills.md, SKILL.md.

Tests: 273 functional + 40 security = 313 green.
